# 考试业务需求说明（团队评审稿）

> 文档目的：汇总当前已达成共识的**考试相关业务规则**与**实现边界**，供团队评估工作量、风险与迭代顺序。  
> 适用范围：在线考试系统中与「考试管理、试卷、学生参考、冻结与快照、应急撤销」相关的功能。  
> 状态：**评审稿**（可与产品/教务流程再对齐后定稿）。

---

## 1. 背景与目标

### 1.1 业务目标

- 支持教师创建考试、发布试卷、在考试开始前维护题库与组卷。
- 支持符合条件的学生们在指定时间窗口内参加同一场考试。
- 同一场考试内，全体考生题目内容一致（不因进入时间不同而拿到不同版本的试卷）。
- 在考试关键节点前锁定试卷内容，避免开考后临时改题带来的公平性与审计问题。
- 超级管理员遇到意外状况可撤销考试，并强制写审计日志（谁、何时、原因、哪场考试、关联老师、关联学生）

### 1.2 非目标（当前迭代可明确排除或后置或不考虑）

- 考试可分为学生灵活选时间考试（比如一天内的某两个小时自主考试）或硬性时间规定（只能在特定日期的特定时间统一考试），目前暂定先实现后者。如果此项通过，需再商议灵活选时间考试的试卷同步问题。
- 公告系统，即发布考试、考试通知、撤销考试等需向老师、学生通知。
- 客观题机器阅卷，填空题模糊阅卷，主观题人工阅卷全流程（若需要，可作为独立迭代）。
- 复杂防作弊（除非单独立项，对于此简单项目我们团队一般不考虑此项，过于复杂）。

## 2. 术语

| 术语 | 说明 |
|------|------|
| 考试 | `exam_manage` 中的一条记录，主键为 `examCode`。 |
| 试卷 | 通过 `paperId` 关联 `paper_manage` 中的题目组合。 |
| 冻结时刻 | 试卷内容**不可再改**的业务时间点（见第 4 节）。 |
| 本场共用快照 | 同一场考试（`examCode`）下**全体考生共用**的一份题目内容快照（冻结后生成）。 |
| 考试会话 / 作答会话 | 学生进入考试后产生的个人记录（如 `exam_attempt`），用于交卷、判分与追溯。 |

---

## 3. 角色与权限（摘要）

| 角色 | 与考试相关能力（摘要） |
|------|-------------------------|
| 教师 | 创建/维护/发布考试与试卷（受冻结策略约束）；查看成绩等（若接口具备）。 |
| 学生 | 在允许时间进入考试、答题、交卷（以接口实现为准）。 |
| 超级管理员 | **撤销考试**等应急操作，并产生**审计日志**（见第 7 节）。 |

---

## 4. 时间与地区规则

### 4.1 服务器时间

- **统一使用 `Asia/Shanghai`（东八区）** 进行业务时间计算与日志时间解释。

### 4.2 冻结策略

- 在**考试正式开始前 1 小时**到达「**最终版**」状态：此后试卷内容**冻结**（若为灵活自主考试则另需商议）。
- 冻结后**生成本场共用快照**（见第 5 节），保证同场题目一致。

> 实现提示：建议显式存储 `freeze_at`（或由 `exam_start + 规则` 推导），试卷状态机等，避免前后端各算各的。

### 4.3 考试开放窗口（与现有实现对齐时需统一）

当前后端实现中，考试窗口大致为：`examDate` 当天 **00:00（上海）** 起，持续 `totalTime` 分钟（若未配置则默认 90 分钟）。  

**目标：**老师创建试卷后自己设计发布时间和持续时长，默认立即发布和持续90分钟。

**评审需确认**：是否与教务真实需求一致（例如是否需要「开考具体时刻 + 时长」而非「整日 0 点起算」，是否需要灵活自主考试方案）。

---

## 5. 试卷冻结与快照

### 5.1 冻结后要达成的效果

- **同场考试题目完全一致**：全体考生读取**同一份本场共用快照**，建议不采用「每位考生进入时再各自生成一份可能不一致的快照」方案。

### 5.2 冻结后禁止修改的内容

冻结后**禁止**包括但不限于：

- 换卷（更换绑定的 `paperId`）
- 增删题目、改题目顺序
- 改分值
- 改题干、选项、标准答案等一切影响题目内容或判分结果的修改

### 5.3 冻结后仍允许修改的内容

仅允许修改**低风险字段**：

- 考试说明类文案（字段集合需在数据模型中写死，例如 `description` 等）
- 考生须知 `tips`
- 考试时长 `totalTime`（如果允许）

#### 时长变更附加规则（如果允许）

- **只允许增加** `totalTime`，**禁止减少**。
- 修改后需 **全员统一重算** 与考试结束相关的截止时间（具体计算规则须与第 4.3 节的窗口定义一致，并在接口层保证幂等与可追溯）。

---

## 6. 学生参加考试（业务规则摘要）

### 6.1 资格校验

- 学生需满足考试设定的范围条件（如年级、专业、学院等；字段为空表示该维度不限制——与现有实现思路一致）。
- 必须在允许的考试开放窗口内进入（具体以最终时间模型为准）。

### 6.2 与快照的关系（目标态）

- 学生进入考试时，应加载 **本场共用快照**（冻结后已生成），并建立个人会话（用于答题与交卷）。
- **同场所有学生**看到的题目内容应与共用快照一致。

---

## 7. 应急处理与补考策略

### 7.1 超级管理员撤销考试

- 出现突发情况时，**超级管理员**有权**撤销考试**。
- 必须保留**重要审计日志**：至少包含操作者、时间、对象（`examCode` 等）、原因、影响范围说明。

### 7.2 补考 / 重考

- **只能重新开设另一场考试**（新的 `examCode` / 新的组卷流程）。
- **禁止**在「原有问题/原试卷」上继续修改来充当补考。

## 8. 与当前实现的差异说明（供评估改造量）

以下基于仓库中已有代码与脚本的**现状摘要**，用于评估「到目标态还差什么」：

| 方向 | 现状摘要 | 目标态（本文） |
|------|----------|----------------|
| 快照时机 | 曾在「学生进入考试」路径生成快照（每人一份会话下的快照行） | 冻结后生成 **本场共用快照**，学生会话引用同一份 |
| 冻结门禁 | 尚未系统化落地「冻结前后 API 行为差异」 | 冻结后拦截改卷/改题类接口；允许字段走白名单更新 |
| 时长修改 | 需补齐「只增不减 + 全员重算截止时间」（如果允许） | 按第 5.3 节实现 |
| 撤销与审计 | 需新增或补齐管理员撤销与审计表/日志 | 按第 7 节实现 |

## 9. 非功能需求（摘要）

- **时间一致性**：全链路使用上海时区口径，避免日志与业务时间错位。
- **可追溯性**：撤销、冻结、时长变更等关键操作需要可审计。
- **一致性**：同场共用快照与并发（首张生成、避免重复写入）需有明确策略（定时任务或带锁的懒生成）。

## 10. 开放问题

1. **考试开始时刻**：是否仅有 `examDate`（日期）？是否需要「几点开考」？若需要，字段模型如何扩展？  
2. **冻结**的精确时间定义：什么时候冻结试卷，是开始时间前一个小时还是开始后冻结？  
3. **撤销考试**后，已产生的学生会话/成绩/快照如何处理（标记作废、禁止提交、是否通知）？  
4. **共用快照**存储形态：独立表 `exam_paper_snapshot` + 题目行表，还是在 `examCode` 上挂 JSON（团队可权衡查询与扩展性）。

### 12.3 与考试业务相关的结构说明（评审/改造关注点）

- **`exam_manage.examDate` / `examStartAt`**：初版脚本仅有 `examDate`（日期）；若需「几点开考」，需执行增量脚本新增 `examStartAt (DATETIME)`（见 `backend/sql/2026-04-10_add_exam_start_at.sql`），并在变更记录中登记。
- **`paper_manage`**：脚本中**无主键、无唯一约束**，且种子数据存在**同一 `(paperId, questionType, questionId)` 重复行**的可能；与「同场题目一致、去重、计分」相关时，需在后续迁移中评估加约束与数据清洗（变更须留痕）。
- **`exam_attempt` / 本场共用快照**：初版 `online_exam.sql`**未包含** `exam_attempt`、`exam_paper_snapshot`、`exam_shared_snapshot_item`；须按顺序执行增量 SQL（见 12.4），不得在无记录情况下只改本地库。

### 12.4 数据库变更审计要求（建议团队遵守）

凡**表结构、索引、约束、字段语义**发生变化，应至少保留以下信息（可放在 `backend/docs/数据库变更记录.md` 或 Issue/里程碑中，由负责人维护）：

| 记录项 | 说明 |
|--------|------|
| 变更日期 / 版本 | 与发版或迭代对应 |
| 变更人 | 便于追溯 |
| 关联需求/评审文档 | 例如本文档章节或接口文档 |
| 影响范围 | 哪些表、是否破坏兼容、是否需要数据迁移 |
| 脚本 | **增量 SQL** 文件路径（如 `backend/sql/xxx.sql`），禁止仅口头同步 |
| 回滚策略 | 是否可 `DROP`/逆迁移，或备份恢复方案 |
| 验证方式 | 例如关键接口冒烟、样本数据校验 |

**增量脚本（仓库内）**：文件名与建议执行顺序以 `backend/sql/README.md` 为准，避免与本文重复维护两套表。

后续若增加「考试状态」「管理员撤销审计表」等，应同样以**增量 SQL + 变更记录**方式管理。

### 12.5 测试数据与隐私

- `online_exam.sql` 内含**示例账号、题库、成绩**等，仅用于开发测试。
- **禁止**将含真实师生隐私的生产数据未经脱敏直接提交仓库；若需演示数据，应使用合成数据并在变更记录中注明。
