# 当前单体在线考试系统高并发优化分阶段计划

## Summary

- 当前项目是 Vue + Axios 前端直连单个 Spring Boot 3 + Tomcat + MyBatis-Plus + MySQL + HikariCP 后端，没有现成的网关、Redis、MQ、任务调度或读写分离。
- 当前最明显的并发瓶颈不是“机器不够”，而是热点链路设计偏串行和重库：前端存在列表页补请求和频繁保存；后端存在 ORDER BY RAND() 自动组卷、select * 与全量拉取、学生交卷逐题查库、教师考试列表 N+1 查策
  略、考试快照仅靠单 JVM 锁、生产环境仍开 SQL stdout 日志。
- 目标按“中等校园级”设计：几千在线、核心接口几百到一两千 QPS、开考和交卷时存在明显峰值；路线以“单体增强”为主，不先拆微服务，但允许引入 Nginx + Redis + RabbitMQ + MySQL 主从。
- 目标拓扑定为：Browser -> CDN/静态缓存 -> Nginx 反向代理/限流 -> 多实例 Spring Boot -> Redis/Caffeine -> MySQL 主从 -> RabbitMQ 异步消费。
- 优化顺序必须从“观测与减请求”开始，再做“热点链路代码减载”，然后再上缓存、异步和数据库扩展；否则会把低效请求更快地放大。

## Important Changes

- 前端请求入口统一改为相对路径 /api，由 Nginx 反代，不再在前端写死 http://localhost:8080。
- 考试列表类接口改为一次返回页面所需的全部状态字段，避免列表页逐项补查策略；教师考试列表也应参考学生侧已做的聚合返回思路。
- 写接口统一支持幂等控制，至少对 login/refresh、attempt/start、attempt/submit、score 相关写入加幂等键或唯一约束兜底。
- 学生答题保存接口改为“前端本地缓冲 + Redis 草稿 + 定时/事件刷库”模式，数据库不再承受每次输入即写。
- 增加内部异步事件契约：exam.submitted、exam.revoked、score.statistics.rebuild、message.created、auth.refresh.revoked。
- 增加统一观测接口与指标暴露，推荐接入 Spring Boot Actuator + Micrometer + Prometheus，并输出 /actuator/health、/actuator/prometheus。

## Phase 0: 基线、容量模型与可观测性

- 先建立容量模型，明确三类峰值场景：考前 10 分钟登录与考试列表高峰、开考前后 attempt/start 高峰、交卷截止前 5 分钟 attempt/submit 高峰；所有后续配置以这三个峰值为目标。
- 补齐基础监控后再优化，最低要求包括：应用 QPS、P95/P99 延迟、Tomcat 活动线程数、JVM 堆与 GC、Hikari 活动连接数、MySQL 慢查询数、Redis 命中率、RabbitMQ 堆积深度、Nginx upstream 状态。
- 关闭生产 SQL stdout 日志，保留 warn/error 和可控的慢 SQL 日志；当前 mybatis-plus.configuration.log-impl=StdOutImpl 必须在生产 profile 下移除。
- 给关键入口打业务指标：/auth/login、/auth/refresh、/student/exam/*、/answer/submit、/scores/*、/question-bank/*、/messages/*。
- 用 k6 建立最小压测脚本并纳入仓库，至少覆盖登录、考试列表、开始考试、暂存答案、交卷、题库分页六条链路；后续每一阶段都复用同一套脚本回归。
- 本阶段验收标准：可以稳定拿到每条关键链路的吞吐、延迟、错误率与数据库负载数据，并能定位最慢 SQL 与最重接口。

## Phase 1: 前端请求治理与静态资源减载

- 先降低请求量，再谈后端扩容；前端必须把高频、重复、扇出请求收敛掉。
- 所有前端 API 改为走 /api 相对路径，由 Nginx 转发；静态资源由 Nginx 直接托管，开启 gzip，并为 JS/CSS/图片加长缓存头。
- 列表页禁止逐项补查；当前教师考试列表存在 getExamPolicy(examCode) 的 N 次补请求，应改为分页列表一次返回考试状态、冻结状态、窗口时间和撤销状态。
- 对搜索、筛选、分页类请求增加前端防抖；用户输入不直接触发后端查询，统一做 300ms 到 500ms debounce。
- 学生答题自动暂存从“变更后 900ms 写库”改为“本地合并变更 -> 3 到 5 秒批量发送 -> 页面隐藏/离开时强制 flush”；这样可直接降低保存请求量。
- 对考试详情、考试列表、成绩统计、消息回复列表做短时内存缓存和请求合并，同一个页面/路由生命周期内相同请求只发一次。
- 对需要秒级倒计时的页面只做本地计时，严禁为了倒计时每秒向后端轮询；当前学生答题页和考试详情页已经以本地计时为主，这条必须保持。
- 本阶段验收标准：前端总请求数明显下降，教师考试列表不再出现 N+1，学生答题保存请求频率显著下降，静态资源不再穿透到应用服务。

## Phase 2: 网关、负载均衡与入口保护

- 第一阶段网关不引 Spring Cloud Gateway，直接使用 Nginx 作为入口层；原因是当前仍是单体，Nginx 足够承接 TLS、静态资源、反向代理、限流和多实例负载。
- Nginx 负责四件事：静态资源托管、/api 反代、限流防刷、健康检查与 upstream 负载均衡。
- 负载均衡策略优先用 least_conn 或 ip_hash 的审慎组合；鉴于 JWT 是无状态的，常规 API 不需要 session stickiness，但考试相关写接口如仍依赖本地缓存则必须先消除本地状态后再扩容。
- 对 /auth/login、/auth/refresh、/student/exam/*/attempt/start、/student/exam/*/attempt/submit 单独配置限流与熔断保护，限制恶意刷接口和误重试风暴。
- 入口层开启 keepalive、合理的 proxy_read_timeout、client_body_buffer_size、client_max_body_size，防止慢连接和大包压垮 Tomcat。
- 应用服务改为至少双实例部署，实例之间无本地状态依赖；考试快照生成、作答状态、令牌刷新状态等都不能只依赖 JVM 内存。
- 本阶段验收标准：在不改业务语义的前提下，入口层可以把静态资源和 API 分流，多实例应用服务能稳定横向扩容，且对登录和交卷峰值具备基础限流能力。

## Phase 3: 应用服务热点链路重构

- 当前最先要改的是“高并发下最重的代码路径”，而不是先全量做架构拆分。
- 自动组卷必须替换 ORDER BY RAND()；当前三类题目随机抽题都在 SQL 层做随机排序，这在题库增大后会直接拖垮数据库。替代方案定为“先按科目和题型维护可抽题 ID 集合，再由应用侧随机采样并批量落库”。
- 学生交卷必须去掉逐题查库；当前判分阶段对每题调用 findByQuestionId，是典型 N+1。改为在考试快照生成时同时缓存本场“正确答案映射”，交卷时一次性读取后在内存比对。
- 冻结试卷构建也要去掉逐题查库；当前共享快照转完整题面同样按题逐条查询，必须改成按题型批量查询后在内存重组。
- 学生考试列表不能再“查全表后在 Java 中按年级/专业/学院过滤”；应改为 DB 侧动态 SQL 过滤，减少全表扫描、对象创建和网络传输。
- 题库聚合分页当前是 UNION ALL 三张题表再 count/page，需要改为查询条件前置、必要字段投影和缓存化；热点场景下禁止每页都执行完整 union count。
- JWT refresh 当前每次都查 MySQL 并回写 revoke；第一阶段保持 DB 作为最终一致来源，但增加 Redis 热缓存以减轻读压，避免高峰期 refresh 全打数据库。
- 考试快照生成当前只靠 ConcurrentHashMap<Integer,Object> 单 JVM 锁；一旦多实例部署会失效。必须改为 Redis 分布式锁或基于唯一约束的数据库幂等生成策略。
- 统一为所有高峰写接口做幂等保护：attempt/start、attempt/submit、score.add、auth.refresh 都要保证重复请求不会重复插入或重复扣状态。
- 本阶段验收标准：最重链路的 CPU、SQL 次数、单请求 DB round-trip 显著下降；单实例吞吐提升后，再进入缓存与数据库扩展阶段。

## Phase 4: 缓存体系建设

- 缓存分为两层：应用内 Caffeine 做超热短 TTL 本地缓存，Redis 做跨实例共享缓存；两层都必须有明确的 key 和 TTL 策略。
- Caffeine 只缓存读多写少、变更频率低的元数据，例如考试策略、题型汇总、题库筛选结果、学院/专业字典、热点考试详情；TTL 建议 30 秒到 3 分钟。
- Redis 重点缓存四类数据：考试元数据与状态、冻结快照题面与答案映射、学生作答草稿、鉴权热数据。
- 学生作答草稿改为 Redis 主存储，key 以 examCode + studentId 组成，设置考试结束后短期 TTL；后端保存接口优先写 Redis，周期性或关键事件刷入 MySQL。
- 考试共享快照与正确答案映射以 examCode 为粒度缓存，生成后主动回填缓存；attempt/start 和 attempt/submit 都先读 Redis，MySQL 只做回源和兜底。
- 对考试列表和详情采用 cache-aside，变更事件包括：考试编辑、冻结、撤销、时长修改、题库删除、组卷变更；这些写操作必须同步删除相关缓存。
- Refresh token 热状态缓存为 jti -> {revoked, expiresAt}，TTL 与 token 一致；DB 保持权威，Redis 为读优化层。
- 限流、分布式锁和热点保护也统一落到 Redis，不在应用内存各自实现。
- 本阶段验收标准：热点考试相关读请求大部分命中 Redis/Caffeine，数据库主要承担回源与持久化而不是每次实时计算。

## Phase 5: 数据库与 SQL 优化

- 在现有单体架构下，数据库仍是最终瓶颈，所以这一阶段要先做“结构和 SQL 优化”，再做“主从扩展”。
- 先补核心索引。首批必须包含：paper_manage(paperId, questionType, questionId) 唯一或主键级约束、score(examCode, studentId) 唯一索引、score(studentId, scoreId)、score(examCode)、
  exam_manage(exam_start_at)、exam_manage(grade, major, institute, exam_start_at)、必要的 revoked_at / paper_frozen_at 辅助索引。
- 对 paper_manage 补唯一约束前先做数据清洗，因为当前结构没有主键和索引，重复题目关系会直接放大后续查询与快照复制成本。
- 逐步消除 select *，改成 DTO 投影和覆盖索引友好的字段集合，尤其是 exam_manage、score、student、teacher、message、题库相关 mapper。
- 将学生考试列表、成绩列表、消息列表等高频查询改成“查询条件明确 + 排序字段有索引 + 结果字段有限”的标准分页 SQL。
- 关闭无用事务放大，缩小事务边界；像答题保存、交卷、快照生成、刷新令牌撤销要严格区分“必须同事务”和“可异步后置”的步骤。
- 增加慢查询日志与 SQL 审计，所有进入 P95/P99 高延迟的 SQL 都需要在索引、SQL 重写或缓存三个方向中给出明确处理手段。
- 第二阶段数据库扩展定为 MySQL 一主一从：写走主库，考试列表、题库分页、成绩统计、消息列表、教师考试查询等读多接口迁移到从库；主从延迟超过阈值时自动回退主库。
- 本项目在中等校园级目标下不做分库分表，除非压测证明单主单从 + 缓存仍无法支撑；否则分库分表会过早增加复杂度。
- 本阶段验收标准：核心查询走上正确索引，慢 SQL 数量显著下降，主库写压可控，从库能稳定承接读流量。

## Phase 6: 异步系统与削峰填谷

- 异步层选型定为 RabbitMQ，不在第一轮上 Kafka；原因是当前系统事件量中等、业务简单、团队更适合先上轻量队列。
- 采用“同步返回必要结果，异步处理派生结果”的原则。交卷接口同步完成资格校验、答案比对、最终成绩落库和考试状态切换；统计汇总、消息通知、审计扩展、报表重建走异步事件。
- exam.submitted 事件用于异步更新成绩统计缓存、排行榜、通过率、教师端报表；不再在交卷主线程里做二次聚合。
- exam.revoked 事件用于异步清缓存、通知前端消息系统、重建考试状态投影。
- 学生暂存草稿的 MySQL 落库采用批量异步刷盘，而不是每次编辑都立即刷；但交卷前必须强制同步 flush 一次，保证最终一致。
- 所有事件采用 Outbox 模式或“本地事务表 + 消费确认”模式，禁止单纯“数据库提交后直接 fire-and-forget 发消息”，避免数据库成功但 MQ 失败造成状态丢失。
- 消费端必须幂等，至少对 examCode + studentId + eventType 建幂等消费记录，避免重复投递导致重复统计或重复通知。
- RabbitMQ 主要承接峰值削峰，不承担核心强一致业务判定；考试资格、交卷幂等、刷新令牌合法性仍由同步链路控制。
- 本阶段验收标准：交卷和考试编辑主链路只做必要同步步骤，统计和通知不再阻塞用户响应；高峰下 MQ 可控堆积但不会影响核心接口成功率。

## Phase 7: 应用容器与资源调优

- 在完成前几阶段减载后，再调 Tomcat 和 Hikari；否则只是把低效请求更快打到数据库。
- Tomcat 建议按实例先从 maxThreads=200~300、acceptCount=500~1000、maxConnections=4096~8192 起步，并根据压测结果收敛，不直接把线程数拉到过高。
- Hikari 连接池按“实例数 * 单实例最大连接数 <= MySQL 可承受连接总数”反推，首轮建议每实例 30~40，两到四实例场景配合主从后再细调。
- JVM 建议固定堆大小，启用 G1，避免考试峰值时因频繁扩缩堆影响延迟。
- 日志使用异步 appender，避免同步 IO 在高峰时拖慢请求线程。
- 读多热点服务可以水平扩容到 2 到 4 实例；写多峰值仍优先靠缓存和异步削峰，不靠无限堆线程。
- 本阶段验收标准：在同样压测流量下，Tomcat 线程、数据库连接和 JVM GC 都保持稳定，没有明显的线程耗尽或连接池打满。

## Phase 8: 验证、灰度与上线节奏

- 每一阶段都必须先做单独压测，不允许所有优化堆到最后一次联调。
- 压测场景至少包含：登录洪峰、考试中心列表、教师考试列表、开始考试、答题暂存风暴、交卷风暴、题库分页、消息分页。
- 灰度顺序定为：先上 Nginx 和静态资源托管，再上前端减请求，再上线应用热点链路重构，再上 Redis 缓存，最后上 RabbitMQ 和数据库主从。
- 每上线一个阶段都要回归“考试开始、保存答案、交卷、成绩查询、管理员撤销”五条关键业务链，确保性能优化不破坏考试正确性。
- 建立降级预案：Redis 不可用时回退 DB 但关闭高频暂存；RabbitMQ 堵塞时停派生统计消费者但保留同步交卷；从库延迟过高时读流量回切主库；极端流量下可临时限制题库与消息等非核心功能。
- 本阶段验收标准：每个阶段都有独立回滚面，峰值场景下核心考试链路优先级最高，非核心功能可降级但不拖垮主链。

## Test Plan

- k6 建立版本化压测脚本，输出登录、列表、开始考试、保存答案、交卷、统计查询的 P50/P95/P99、RPS、错误率。
- 压测前后统一抓取应用指标、Nginx 指标、Redis 指标、RabbitMQ 指标、MySQL 慢查询和连接数，形成每阶段对比表。
- 对幂等性做专项验证：重复点击开始考试、重复提交交卷、重复 refresh token、重复消息消费都只能产生一次最终效果。
- 对一致性做专项验证：多实例下共享快照只能生成一次；Redis 草稿与最终交卷内容一致；异步统计延迟可接受且最终正确。
- 对降级做专项演练：模拟 Redis 失效、MQ 堵塞、从库延迟、单实例宕机、Nginx upstream 下线。
- 验收阈值建议：核心考试接口错误率 < 0.1%，交卷 P95 可控，峰值期间 MySQL 不出现连接池耗尽和长时间锁等待。

## Assumptions

- 本计划按“单体增强”执行，不以首轮微服务拆分为目标；Nginx 是第一阶段入口层，不引入 Spring Cloud Gateway。
- 目标压力按“中等校园级”设计，不做分库分表与 Kafka 级大规模事件平台。
- Redis 采用共享单集群或哨兵/主从部署；RabbitMQ 采用单集群高可用部署；MySQL 采用一主一从起步。
- 交卷仍要求同步返回成绩，因此“判分”本身不异步化；异步化的是统计、通知、报表和缓存重建。
- 当前考试系统的核心高并发对象是“考试开始、答题暂存、交卷、考试列表/详情”，消息和题库属于次级负载，优化优先级低于考试主链。

## Key Changes

- 新文档结构定为“现状分析 + 分阶段路线图 + 配置建议 + 验证方案”，不只给结论，也要把当前代码中的具体瓶颈点写清楚。
- 文档开头先固定当前系统画像：
    - 前端：frontend/src/utils/request.js 里 baseURL 直指 http://localhost:8080，无 /api 网关前缀。
    - 后端：backend/src/main/resources/application.properties 只有单实例端口与 MySQL 连接配置，无 Redis/MQ/网关配置。
    - 运行容器：Spring MVC + Tomcat，不是 WebFlux；数据库连接池是 HikariCP。
    - 持久层：大量 MyBatis 注解 SQL，存在 select *、全表分页、UNION ALL 聚合分页等典型压力点。
- 文档正文必须显式列出当前热点瓶颈，至少包括：
    - 自动组卷三类题型都使用 ORDER BY RAND() LIMIT n，属于典型高并发禁用 SQL。
    - 学生交卷在 StudentExamSessionServiceImpl 中按题逐条 findByQuestionId 判分，存在 N+1 查库。
    - 冻结快照读取在 ExamSnapshotServiceImpl 中按题逐条回表，存在另一条 N+1。
    - 教师考试列表前端使用 Promise.allSettled(getExamPolicy) 做逐场补请求，列表放大后会放大后端压力。
    - 学生答题自动保存仍是高频写路径，需要明确改为缓冲、合并、降频。
    - 生产环境仍开启 mybatis-plus.configuration.log-impl=StdOutImpl，高并发下会放大 IO 开销。
    - paper_manage 原始脚本无主键/唯一约束，score 原始脚本只有主键 scoreId，未围绕热点查询建立完整索引。
    - 刷新令牌 auth_refresh_token 目前完全走 MySQL，不具备缓存减压层。
    - 考试快照生成当前依赖 JVM 内 ConcurrentHashMap 锁，多实例后不成立。
